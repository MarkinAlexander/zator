# Быстрый подбор «F» — текущая реализация и планы переделки

Ветка: только `feat/dpi-detect-autoselect` (песочница). Из основной
`zator` удалён по решению владельца: реализация концептуально не нравится
и будет переделываться. Замеры и исследование — `docs/autoselect-research.md`.

## Как работает сейчас (`lib/autoselect.sh`, пункт «F»)

```
F
│
▼ ШАГ 1  baseline-гейт: временный лок 0 → HEAD-проба без докачки
│         отвечает? → «не блокируется, подбор не нужен» — ВЫХОД
│         (в авторском orch_auto_sweep это самая большая пустая работа:
│          43 стратегии гонялись даже по незаблокированным доменам)
▼ ШАГ 2  отсев: порядок = [топ-3 из autoselect.tsv] + остальные по номеру
│         каждая: лок N → пауза ≥ TTL кэша (3с) → HEAD-проба (Z2R_TLS_NO_DL=1,
│         патч движка netcheck.sh — без докачки)
│         стоп после K=3 зелёных (Z2R_AUTOSELECT_K)
▼ ШАГ 3  ранжирование финалистов: полная проба с докачкой 64КБ,
│         лучшая = max байт/с (метрика авторского прогона)
▼
Enter = лучшая / номер зелёной / 0 = прежние локи
победа → cache/orchestra/autoselect.tsv (ключ/стратегия/побед/время,
топ-10 на ключ) — следующий запуск начинает с неё
```

Рестарт nfqws2 не нужен (локи через locked.tsv, TTL 2с). Ctrl+C: локи
восстанавливаются, упавший nfqws2 перезапускается (safety net из
orch_auto_sweep). Оценки: типично 60–70с вместо 5,5–10 мин полного
прогона; повторный warm-запуск 30–40с; худший случай (зелёных нет)
43×10,4с ≈ 7,5 мин (живой замер).

## Что НЕ нравится (зафиксировано для переделки)

1. Реализация подбора в целом не устраивает владельца — «быстрые проверки
   и т.д. пока не нравятся».
2. смежное, из авторотации автора (`circular_quality`): хосты, которым
   обход не нужен, жёстко закрепляются на стратегии 1 (3 успеха из 5 →
   lock) — «она не ломает, но и не нужна». Правильнее: не-нуждающийся
   хост не лочить вообще / уводить в pass-through.
3. Подбор реактивен по своей природе: без живого трафика авторотация
   ничего не подбирает; F генерирует свои пробы, но это «проверка по
   кнопке», а не «включил и забыл».

## Направления переделки (обсуждаемое)

- Связка уже есть в `zator`: детект сломанности + RAM-кэш вердиктов
  (`docs/break-detect.md`) — она гарантирует «рабочие сайты в любом
  режиме». Следующий шаг — «нуждающийся в обходе»-детект: домен падает
  без обхода → мини-подбор только для него → per-host лок.
- Параллельные инстансы nfqws2 через `--filter-mark` (уже в master форка
  zapret2) — проверять несколько стратегий одновременно.
- Снижаемый `cache_ttl` локов (сейчас 2с — структурный пол 3с на
  переключение).
- Учёт наказания ТСПУ за перебор (живое наблюдение из research-док):
  warm-кэш и baseline-гейт не оптимизация, а необходимость.
